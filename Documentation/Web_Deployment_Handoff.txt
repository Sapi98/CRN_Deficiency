============================================

Branch: web_app

1. PURPOSE AND SCOPE
-------------------
Host a Python web application for chemical reaction network analysis.
Users upload/paste equations or reactions, explore interactive network graphs,
and download deficiency reports. Only the web service needs hosting; desktop
distribution and Python package publishing are outside this request.

Deploy from the repository: web/ provides the interface and crntanalysis/
provides its analysis backend. Use requirements-web.txt, not setup.py or the
general project's requirements.txt.

2. SOFTWARE AND DEPENDENCIES
---------------------------
Proposed production runtime: Linux, CPython 3.12 (python:3.12-slim), Gunicorn,
and Docker or an equivalent institution-managed Python hosting environment.
No database, GPU, Node/npm build, or desktop Qt stack is required.

3. DEPLOYMENT
-------------
From the repository root on a Docker-capable Linux server:

  git switch web_app
  docker build -f Dockerfile.web -t crntanalysis-web .
  docker run -d --name crntanalysis-web --restart unless-stopped \
    --memory=2g --cpus=2 -p 127.0.0.1:8050:8050 crntanalysis-web
  curl --fail http://127.0.0.1:8050/healthz

Expected health response: {"status":"ok"}.

The image runs as unprivileged user crnt (UID 10001). Its startup command is:

  gunicorn --bind 0.0.0.0:8050 --workers 2 --threads 1 --timeout 35 \
    web.wsgi:server

Put an institutional HTTPS reverse proxy in front of port 8050. Keep that port
private; expose the approved HTTPS endpoint instead. Do not use the development
server for production. Managed Docker hosting should use Dockerfile.web,
repository-root build context, web_app branch, and health path /healthz.
The current command binds to fixed port 8050; set PORT=8050 if the platform
requires a matching environment variable, or override the startup command.

4. CAPACITY, DATA HANDLING, AND ACCESS
------------------------------------
Start evaluation at approximately 2 vCPU and 2 GB RAM, then benchmark realistic
concurrent workloads. This is an estimate, not a capacity guarantee: two large
analysis children plus web workers can exceed the example 2 GB container cap.

Current limits:
  Input: 32,000 bytes; HTTP body: 2,500,000 bytes; result: 1,000,000 bytes.
  Graph: 500 complexes / 1,500 reactions.
  Analysis: 20 seconds in a separate spawned process.
  Linux child address space: 1 GiB. Gunicorn timeout: 35 seconds.
  Two synchronous web workers; requests can queue during analysis.

Models are processed in server memory and may contain unpublished research.
The app does not save uploads/reports to disk or maintain a user-result cache.
Results use browser memory; downloads are user-initiated. There is no database.
Infrastructure logs, swap, dumps, and browser behavior remain subject to IT
policies; these statements do not guarantee secure erasure.

There is NO built-in login, SSO, or rate limiter. For restricted use, provide
institutional sign-in, an authenticated proxy, or VPN access. HTTPS alone is
not access control. Add request-rate limits and enforce CPU/memory limits.
Avoid request-body logging. This is not a general-purpose execution sandbox.
No private research inputs or generated reports are copied by Dockerfile.web.
