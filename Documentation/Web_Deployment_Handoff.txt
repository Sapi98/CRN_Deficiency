1. APPLICATION PURPOSE AND DEPLOYMENT SCOPE
-------------------------------------------
CRNTAnalysis analyzes chemical reaction networks (CRNs). Users paste a model
or upload a UTF-8 .react, .ode, or .txt document. The server parses the model,
constructs a network realization, calculates whole-network and linkage-class
deficiencies, and returns equations, graph data, and reports. Supported optional
ODE transformations include reciprocal auxiliary-species embeddings and
fractional-power real-complex realizations.

The browser interface provides interactive reaction/linkage graphs, node/edge
inspection, layout selection, linkage filtering, text search, PNG export, and
plain-text/structured report downloads. Calculations run on the server; visitors
need only a supported browser and the hosted application URL.

the IT team is being asked to provision and operate the web hosting environment:
deployment, HTTPS/domain configuration, access controls, resource limits,
monitoring, and infrastructure updates. No desktop installation, executable
distribution, or Python package publishing is requested. Scientific algorithms
and application feature development remain with the research/software team,
subject to an agreed maintenance arrangement.

Deploy the web_app repository branch using Dockerfile.web and
requirements-web.txt. The hosted service needs two source directories:
web/ (browser interface/server adapter) and crntanalysis/ (its Python analysis
backend). The latter is part of the web service, not a separate application
the IT team must distribute. Do not run setup.py or install the general project
package to provision this service; the Docker recipe installs only web needs.


2. ARCHITECTURE AND REPOSITORY FILES
------------------------------------
Request flow:
  Browser -> HTTPS reverse proxy -> Gunicorn -> Flask/Dash callback
          -> spawned Python analysis process -> CRNAnalysisService / SymPy
          -> JSON result -> browser Cytoscape graph and downloadable reports

The Python backend performs scientific analysis; the browser handles presentation
and graph interaction. Scientific calculations are not reimplemented in JavaScript.

Relevant paths:
  web/app.py               Dash app factory, layout, callbacks, local launcher.
  web/service.py           Upload validation, analysis isolation, graph adapter.
  web/wsgi.py              Production WSGI entry point: web.wsgi:server.
  web/assets/workspace.css Local browser stylesheet; no external font import.
  crntanalysis/            Shared parsers, symbolic models, deficiency, reports.
  requirements-web.txt    Direct headless web requirements and version ranges.
  Dockerfile.web          Proposed Linux container deployment recipe.
  .dockerignore           Allowlist of files sent to Docker builds.
  tests/test_web.py       Adapter, process, HTTP callback, and packaging tests.
  README.md               General launch and hosting instructions.
  Documentation/web_app.md Detailed web operations and developer API.
  LICENSE                 Project's PolyForm Noncommercial License 1.0.0.

The Dockerfile explicitly copies crntanalysis/, web/, requirements-web.txt,
and LICENSE. Private Research_Models/, generated research reports, .git/,
virtual environments, and GUI/ are not included in its build context/image.
Generic web examples are embedded in web/service.py.

---------------------------------------------------

  - CPython 3.12 via the existing python:3.12-slim base image.

  sympy>=1.13,<2
  dash>=3.0,<4
  dash-cytoscape>=1.0,<2
  gunicorn>=23,<24; platform_system != 'Windows'

  SymPy: restricted arithmetic expressions, symbolic algebra, chain-rule ODE
         construction, and symbolic/exact stoichiometric rank calculations.
  Dash: Python-defined web UI, reactive HTTP callbacks, upload/download controls.
  dash-cytoscape: browser network visualization, graph interaction, PNG export.
  Gunicorn: production UNIX WSGI serving and worker concurrency.

No additional desktop stack, JavaScript build toolchain, database, task broker,
or GPU is required. Install only the web requirements and their resolved
dependencies listed below; unrelated repository requirements are out of scope.

No apt packages are explicitly installed by Dockerfile.web. The slim base

MarkupSafe can use native extension wheels. If wheels are unavailable for an
approved architecture/version, a build toolchain may be needed at image build
time; verify this on the actual platform instead of adding compilers to the
runtime image by default.

6. PRODUCTION INSTALLATION AND STARTUP
--------------------------------------
Preferred deployment uses the repository Dockerfile:

  git switch web_app
  docker build -f Dockerfile.web -t crntanalysis-web .
  docker run -d --name crntanalysis-web --restart unless-stopped \
    --memory=2g --cpus=2 -p 127.0.0.1:8050:8050 crntanalysis-web
  curl --fail http://127.0.0.1:8050/healthz

The proposed image:
  - Base: python:3.12-slim (floating tag; not pinned to an immutable digest).
  - Working directory: /app.
  - Build install: pip install --no-cache-dir -r requirements-web.txt.
  - Runtime user: crnt, UID 10001, not root.
  - Runtime port: 8050.

Exact default server command:
  gunicorn --bind 0.0.0.0:8050 --workers 2 --threads 1 --timeout 35 \
    web.wsgi:server

If containers are not approved, use an IT-managed Linux CPython 3.12 virtual
environment, install requirements-web.txt, and run the same Gunicorn command
from the repository root under systemd or an equivalent process supervisor.
Provide Python multiprocessing/process-spawn support. Gunicorn is not the
Windows production-server option; the intended production target is Linux.

Do not use the Flask/Dash development server as the public production service.
the IT team's hosted runtime should use the Gunicorn WSGI entry point above.

Managed Docker hosting can use branch web_app, repository-root build context,
Dockerfile.web, and /healthz. If the platform uses a PORT environment setting,
set PORT=8050 to match the current fixed server command. The Dockerfile does
NOT dynamically substitute PORT. Override its command if the host requires a
different listening port.

8. DATA HANDLING, CONFIDENTIALITY, AND AUTHENTICATION
-----------------------------------------------------
Potential content: unpublished scientific model equations, parameters, reaction
networks, initial values, and derived analysis. The app does not intentionally
request personal, clinical, financial, or credential data. User uploads can
nevertheless contain confidential text; agree on an appropriate data category
with the researchers before opening the service.

Processing:
  - The model leaves the browser and is processed in server memory.
  - Base64 upload decoding and validation do not save model files to disk.
  - Results are returned to the browser and stored using dcc.Store in memory.
  - No app-level server result cache or persistent browser localStorage is used.
  - Browser refresh clears the app's result state; tabs use independent stores.
  - Downloads create user-requested local files on the user's computer.
  - Client-side graph layout/PNG export does not require an external renderer.

Do not treat these behaviors as guaranteed secure erasure. Browser memory,
server swap/core dumps, debugging/proxy logs, crash reporting, and endpoint
security systems may retain information outside the app's control. the IT team
must set retention, logging, backup, and incident-response policies accordingly.

Current authentication: NONE. There is no application user account system,
SSO integration, role-based authorization, or built-in request-rate limiter.
HTTPS alone does not restrict access. For collaborator-only use, the IT team
should provide institutional SSO/authenticated reverse proxy, VPN, or another
approved access restriction before granting external access.

Other required review points:
  - TLS termination, allowed hosts, security headers and compatible CSP.
  - Institutional identity/session controls, CSRF/origin policy and rate limits.
  - Disable debug/reloader in production; do not log model bodies.
  - Scope internal app-port access to the reverse proxy.
  - Scan and patch OS, Python, and bundled JavaScript dependencies.
  - No eval/exec of uploaded model programs is intended, but symbolic parsing
    and algebra still need resource controls and hostile-input testing.
  - The app is not a general-purpose code-execution sandbox.


9. RESOURCE LIMITS AND CONCURRENCY
-----------------------------------
Current hardcoded application defaults:
  UTF-8 model text:           <= 32,000 bytes.
  Decoded upload:             <= 32,000 bytes.
  HTTP request body:          <= 2,500,000 bytes.
  Serialized web result:      <= 1,000,000 bytes.
  Interactive graph:          <= 500 complexes and <= 1,500 reactions.
  Per-analysis wall time:     20 seconds (includes worker startup/wait).
  Linux child address space:  1 GiB via resource.RLIMIT_AS.
  Gunicorn timeout:           35 seconds.
  Gunicorn workers/threads:   2 synchronous workers, 1 thread each.

Each analysis gets a fresh spawned process, with results sent over a local
multiprocessing pipe. The child is terminated/reaped after completion, failure,
or timeout. The per-child Linux limit is address-space, not a guarantee about
RSS usage or total container memory. Graph/result-size limits are checked
after scientific construction, not a substitute for analysis-time limits.

Two synchronous workers can occupy two analysis slots per instance. Additional
requests can queue; graph callbacks also share the web worker capacity. This
is not a dedicated distributed job-queue architecture. Public deployments
need rate/concurrency controls; increase capacity only after measurement.

Suggested starting allocation: about 2 vCPU and at least 2 GB RAM for evaluation,
with additional headroom as measured. Two large children plus parent workers
can exceed 2 GB; the example container ceiling is not a guarantee that every
allowed calculation succeeds concurrently. Benchmark representative models.
No GPU is required. Modern browsers need adequate resources for interactive
graphs; models exceeding the hosted limits should be declined with the existing
error response rather than automatically increasing server resource exposure.
